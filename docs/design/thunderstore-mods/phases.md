# Thunderstore Mods — Implementation Phases

> Each phase is self-contained, depends only on the phases named in its preconditions, and is verifiable on its own. Read `design.md` (same directory) first; it defines every contract referenced here. Paths are module-level starting points, not a change list — map the exact edits in each phase's own session. Record what each phase found under its "findings" heading, as `../mod-management/phases.md` does.

Phases 1 and 2 are independent; 3 needs 2; 4 needs 1; 5 needs all. Each ships as its own PR (`just ship` / `just merge`). Bot phases deploy through the normal CI build; image phases through `just game-push valheim dev`. The `drive-the-bot` skill (`just operator tool …`, `just operator gary …`) exercises tools and Gary against the deployed bot without a Discord client.

### Phase 1 findings

- **A Thunderstore search result carries no version at all.** The Cyberstorm listing envelope has `namespace`, `name`, `description`, `download_count`, `categories`, `is_deprecated`, `is_nsfw`, and `last_updated` — and nothing version-shaped. So a search line cannot be acted on: `mod_info` is the only source of the string a pinned entry uses, and `ThunderstoreSearchHeader` says so outright rather than leaving the model to compose one.
- **The two endpoints spell a category differently.** A listing carries category *objects* with a `slug` (`server-side`); a package detail carries display *names* (`Server-side`). They differ only in case, so the classifier matches case-insensitively and no slugifier is needed. This is verified live in both directions (`the_side_categories_are_still_how_this_community_expresses_sidedness`, `a_package_detail_classifies_off_display_names`) — a classifier written against one spelling silently reports `Unknown` for everything reached through the other.
- **`Unknown` sidedness is common, not exceptional.** `ValheimModding-Jotunn` — the community's own modding framework — carries `["Libraries", "Bog Witch Update"]` and no side category at all. The design's "neither means unknown, point the friend at the mod page" rule is therefore the normal path for libraries, not an edge case, and `SideSupport::Unknown` deliberately matches *no* side filter so an untagged package never survives a `server` filter as if the registry had vouched for it. The empty-search result names the side filter as the first thing to drop for exactly this reason.
- **Modrinth's side facets accept `required` *and* `optional`.** Only `unsupported` means "does not apply here", so a side filter built from `required` alone would exclude projects that work fine on that side. Pinned by a unit test on the facet string and by a live narrowing test, since a well-formed facet with the wrong vocabulary matches nothing and looks like an empty registry.
- **`SideFilterNotApplicable` was not created.** Both shipped registries express sidedness, so the result would be unreachable — and an orphaned prompt id fails the annotations test. Add it with the first registry that genuinely can't answer the question.
- **The tool descriptions point at `game_guide`, which lands in Phase 4.** Deliberate, per `design.md` §4, but it means that between this phase's deploy and Phase 4's a `game_guide` call comes back as `UnknownTool`. Harmless (the model recovers and proceeds) and self-healing; worth knowing if the interval widens.
- **The `SearchMods` schema now requires `["game", "query"]`.** Parameter order in the generated schema follows the `tool_schema` mapping order in the file, so `game` leads.

### Phase 2 findings

- **`zip` is pinned at 8.6.0**, not the 9.0.0 line: 9.0.0 is still pre-release (`9.0.0-pre3`, Aug 2026). zip-rs/zip2 is actively maintained — twelve releases across 2026 — so the pin is to a live project, not a stale one. Features: `default-features = false` plus `deflate-flate2-zlib-rs`, which is the pure-Rust deflate backend; the whole rest of the compression vocabulary (bzip2, lzma, zstd, xz, AES) is dropped rather than carried unlinked.
- **The musl static link was verified end to end**, both as `cargo build --release --target x86_64-unknown-linux-musl -p grizzly-supervisor` (`static-pie linked`) and as a full `docker build -f games/valheim/Dockerfile`. Note for anyone repeating it locally: the musl build needs `musl-tools` on the host because `ring` (via rustls) shells out to a C compiler — that requirement predates this phase and is why the Dockerfile installs it.
- **`semver` was not used.** Thunderstore versions are exactly three numeric parts, and `semver::Version` would also accept `1.2.3-alpha` and friends — so a malformed mod-list entry would parse here and become a 404 at launch instead of a named error against the line that wrote it. `PackageVersion` is a three-field struct whose derived `Ord` gives the numeric comparison "the highest version wins" depends on (a string comparison would put `1.10.0` below `1.9.0`).
- **`enclosed_name()` cannot be the path that gets validated.** It *sanitises* — an entry declaring `/etc/passwd` arrives already rewritten to `etc/passwd` — so the absolute-path check silently passed until a fixture caught it. `extract` now judges `entry.name()`, the archive's own claim, and only then uses it.
- **Explicit mod-list entries are resolved before any dependency is followed.** Depth-first from the first line would reach a pinned package as somebody else's dependency, record it at the dependency's version, and discard the pin — silently. Two tests pin the ordering.
- **A provided package is skipped whole, dependencies included.** The image ships the loader pack as a unit; re-deriving its tree would install pieces of a second copy over the one that works.
- **The extraction step is synchronous inside the async reconcile.** It is milliseconds for a handful of DLLs, and the 180-second deadline covers the part that actually takes time (the downloads, which do await). If live verification in Phase 3 shows control requests starving during a first install, the follow-up the design already names — moving the reconcile to a spawned task with its own select arm — applies to the extraction as much as the download.
- **`do_start` and `do_restart` answer "acted" on a refused launch.** Not cosmetic: the bot only runs its verify-and-roll-back loop when the supervisor says it acted, so answering "failed" would skip the loop that reads `/status`, sees `Crashed`, and puts the file back.

## Phase 3 — Valheim enablement and live validation

- **Modules:** `games/valheim/Dockerfile` (the three `SUPERVISOR_THUNDERSTORE_*` variables with a comment on the staged→live mirror and why the loader pack is provided; hook renamed); the hook itself (mirror step per `design.md` §3, RCON steps unchanged, `chown` to the game user if verification shows root-owned DLLs are unreadable); `games/valheim/gameserver.yaml` (`SUPERVISOR_MODS_FILE` with the policy-lives-in-the-manifest comment, `failureThreshold` 10); the new drift guard in `crates/bot/src/tests/config.rs`; `games/README.md` (the Valheim bullet — it currently also says Valheim has no console protocol, which stopped being true when ValheimRcon was baked in).
- **Preconditions:** Phase 2 live in the Valheim image.
- **Shape when done:** a Valheim server takes mods through `.grizzly/mods`, the mirror puts them under the live `BepInEx/plugins/<Namespace-Name>/`, the RCON plugin keeps working, and every failure mode below is rolled back or reported.
- **Verification (scratch Valheim server, `just game-push valheim dev`):**
  1. Fresh create: `.grizzly/mods` exists and is empty; `read_logs` shows no install lines.
  2. `write_file` one unpinned server-side mod that has a non-loader dependency → `restart_server` → `[mods] installed` names both; `resolved` lists them; the live plugins dir holds `<Namespace-Name>/…` beside `ValheimRcon.dll`; the BepInEx log shows the plugin loaded; `send_command players` still answers. Record the first-install wall time against the bot's five-minute readiness ceiling.
  3. Pin an older version → restart → `resolved` shows it.
  4. Remove the line → restart → the DLL is gone from the live dir and the cache zip was collected.
  5. `Nobody-DoesNotExist` via `edit_file` → `restart_server` → `/status` reports `Crashed`, the bot restores the snapshot and restarts, the server is healthy, and Gary's result says rollback; the `GameServer` never leaves `Ready`; the pod restart count stays 0.
  6. A malformed line → the same path; the log names the line number.
  7. Offline: a fully cached pinned set restarts with no network and a warning; an unpinned entry warns and uses the highest cached version.
  8. Pod recreation → the mirror re-applies after lloesche's first-boot merge; a bad file on the PVC yields a reachable supervisor reporting `Crashed`, not a container crash loop.
  9. Archive → recover keeps `.grizzly/mods`, its `.grizzly.bak`, and the cache; the recovered boot resolves offline.
  10. A half-configured image (one variable unset in a throwaway push) → startup warning, reconciler inert.
