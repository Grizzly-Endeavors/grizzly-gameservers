# Thunderstore Mods — Implementation Phases

> Each phase is self-contained, depends only on the phases named in its preconditions, and is verifiable on its own. Read `design.md` (same directory) first; it defines every contract referenced here. Paths are module-level starting points, not a change list — map the exact edits in each phase's own session. Record what each phase found under its "findings" heading, as `../mod-management/phases.md` does.

Phases 1 and 2 are independent; 3 needs 2; 4 needs 1; 5 needs all. Each ships as its own PR (`just ship` / `just merge`). Bot phases deploy through the normal CI build; image phases through `just game-push valheim dev`. The `drive-the-bot` skill (`just operator tool …`, `just operator gary …`) exercises tools and Gary against the deployed bot without a Discord client.

## Phase 1 — Registry-aware discovery (bot)

- **Modules:** `crates/bot/src/agones/catalog.rs` and a new `agones/mod_registry.rs` (annotation constants, `ModRegistry`, strict parser, lenient template wrapper); a new `registry/` module (`text.rs` with the truncation helpers and limits hoisted out of `modrinth/types.rs`, `side.rs` with `Side` and `SideSupport`); a new `thunderstore/` module mirroring `modrinth/` (`client`, `query`, `types`, `live`); `modrinth/query.rs` (side facets); `discord/gary/tools.rs` (`registry_for_game` lookup, dispatch by registry, Thunderstore formatters); prompt files: `tools/discord/SearchMods.md` and `ModInfo.md` (add `game`, add `side`, rewrite the bodies registry-neutral as the design approves), new results `results/search_mods/{ThunderstoreSearchHeader,ThunderstoreSearchEmpty,ModrinthFiltersIgnored,SideFilterNotApplicable}.md`, `results/mod_info/{ThunderstorePackageDetail,ThunderstoreNotFound}.md`, `results/shared/{ThunderstoreSummaryLine,ThunderstoreUnavailable,ModGameUnknown,ModsNotSupported}.md`; the `mod-registry` annotations on `games/minecraft/gameserver.yaml` and `games/valheim/gameserver.yaml`.
- **Preconditions:** none.
- **Shape when done:** `search_mods` and `mod_info` require `game`; a Valheim search hits Thunderstore and renders `Namespace-Name`, version, downloads, side support, deprecation, dependencies; a Minecraft search behaves exactly as before plus the `side` filter; a game with no registry gets the not-supported result; an unknown game gets the catalog list. - **Tests:** parser branches in `agones/tests/mod_registry.rs`; a catalog drift guard that loads the real `games/` and asserts minecraft → Modrinth, valheim → Thunderstore{valheim}, every other game none, and that no game hit the lenient warn path; `thunderstore` query/type tests; formatter tests; the `SearchMods` schema test extended for the closed `side` enum; the prompt-annotations test.
- **Verification:** `cargo test --quiet`; run the `#[ignore]` Thunderstore live tests once by hand. After the CI deploy: `just operator tools --access manager` shows the new parameters; `just operator tool search_mods '{"game":"valheim","query":"map","side":"server"}'`; `mod_info '{"game":"valheim","slug":"ValheimModding-Jotunn"}'` and a nonexistent package; a Minecraft datapack search unchanged; `game: factorio` → not-supported; unknown game names the catalog.

### Phase 1 findings

- **A Thunderstore search result carries no version at all.** The Cyberstorm listing envelope has `namespace`, `name`, `description`, `download_count`, `categories`, `is_deprecated`, `is_nsfw`, and `last_updated` — and nothing version-shaped. So a search line cannot be acted on: `mod_info` is the only source of the string a pinned entry uses, and `ThunderstoreSearchHeader` says so outright rather than leaving the model to compose one.
- **The two endpoints spell a category differently.** A listing carries category *objects* with a `slug` (`server-side`); a package detail carries display *names* (`Server-side`). They differ only in case, so the classifier matches case-insensitively and no slugifier is needed. This is verified live in both directions (`the_side_categories_are_still_how_this_community_expresses_sidedness`, `a_package_detail_classifies_off_display_names`) — a classifier written against one spelling silently reports `Unknown` for everything reached through the other.
- **`Unknown` sidedness is common, not exceptional.** `ValheimModding-Jotunn` — the community's own modding framework — carries `["Libraries", "Bog Witch Update"]` and no side category at all. The design's "neither means unknown, point the friend at the mod page" rule is therefore the normal path for libraries, not an edge case, and `SideSupport::Unknown` deliberately matches *no* side filter so an untagged package never survives a `server` filter as if the registry had vouched for it. The empty-search result names the side filter as the first thing to drop for exactly this reason.
- **Modrinth's side facets accept `required` *and* `optional`.** Only `unsupported` means "does not apply here", so a side filter built from `required` alone would exclude projects that work fine on that side. Pinned by a unit test on the facet string and by a live narrowing test, since a well-formed facet with the wrong vocabulary matches nothing and looks like an empty registry.
- **`SideFilterNotApplicable` was not created.** Both shipped registries express sidedness, so the result would be unreachable — and an orphaned prompt id fails the annotations test. Add it with the first registry that genuinely can't answer the question.
- **The tool descriptions point at `game_guide`, which lands in Phase 4.** Deliberate, per `design.md` §4, but it means that between this phase's deploy and Phase 4's a `game_guide` call comes back as `UnknownTool`. Harmless (the model recovers and proceeds) and self-healing; worth knowing if the interval widens.
- **The `SearchMods` schema now requires `["game", "query"]`.** Parameter order in the generated schema follows the `tool_schema` mapping order in the file, so `game` leads.

### Phase 2 findings

- **`zip` is pinned at 8.6.0**, not the 9.0.0 line: 9.0.0 is still pre-release (`9.0.0-pre3`, Aug 2026). zip-rs/zip2 is actively maintained — twelve releases across 2026 — so the pin is to a live project, not a stale one. Features: `default-features = false` plus `deflate-flate2-zlib-rs`, which is the pure-Rust deflate backend; the whole rest of the compression vocabulary (bzip2, lzma, zstd, xz, AES) is dropped rather than carried unlinked.
- **The musl static link was verified end to end**, both as `cargo build --release --target x86_64-unknown-linux-musl -p grizzly-supervisor` (`static-pie linked`) and as a full `docker build -f games/valheim/Dockerfile`. Note for anyone repeating it locally: the musl build needs `musl-tools` on the host because `ring` (via rustls) shells out to a C compiler — that requirement predates this phase and is why the Dockerfile installs it.
- **`semver` was not used.** Thunderstore versions are exactly three numeric parts, and `semver::Version` would also accept `1.2.3-alpha` and friends — so a malformed mod-list entry would parse here and become a 404 at launch instead of a named error against the line that wrote it. `PackageVersion` is a three-field struct whose derived `Ord` gives the numeric comparison "the highest version wins" depends on (a string comparison would put `1.10.0` below `1.9.0`).
- **`enclosed_name()` cannot be the path that gets validated.** It *sanitises* — an entry declaring `/etc/passwd` arrives already rewritten to `etc/passwd` — so the absolute-path check silently passed until a fixture caught it. `extract` now judges `entry.name()`, the archive's own claim, and only then uses it.
- **Explicit mod-list entries are resolved before any dependency is followed.** Depth-first from the first line would reach a pinned package as somebody else's dependency, record it at the dependency's version, and discard the pin — silently. Two tests pin the ordering.
- **A provided package is skipped whole, dependencies included.** The image ships the loader pack as a unit; re-deriving its tree would install pieces of a second copy over the one that works.
- **The extraction step is synchronous inside the async reconcile.** It is milliseconds for a handful of DLLs, and the 180-second deadline covers the part that actually takes time (the downloads, which do await). If live verification in Phase 3 shows control requests starving during a first install, the follow-up the design already names — moving the reconcile to a spawned task with its own select arm — applies to the extraction as much as the download.
- **A cache hit has to hold up, not merely exist.** The first cut skipped the download whenever a file was present at the cache path. A damaged or mislabeled zip would then be permanent: the download is skipped, staging fails on it, and every restart afterwards fails identically with no way out short of deleting the file by hand. Presence is now checked by reading the manifest, and a copy that doesn't hold up is re-fetched with a warning.
- **Two of the phase's stated tests needed a seam to exist at all.** The per-entry and total-expansion caps are 256 MiB and 512 MiB, which no honest fixture reaches, so `extract` grew an `extract_within(..., Caps)` form the tests drive with small caps — plus an assertion that `Caps::DEFAULT` still equals the production consts, or those tests would prove nothing about a real launch. The offline fallback order needed the same treatment: `LayeredSource` is now generic over any `PackageSource` rather than hardcoding the HTTP client, `ThunderstoreApi` implements that trait directly as the uncached layer, and the layering is tested over a fake registry that records what it was asked — which is what lets a test assert the cache was consulted *first* rather than merely consulted.
- **`do_start` and `do_restart` answer "acted" on a refused launch.** Not cosmetic: the bot only runs its verify-and-roll-back loop when the supervisor says it acted, so answering "failed" would skip the loop that reads `/status`, sees `Crashed`, and puts the file back.

## Phase 3 — Valheim enablement and live validation

- **Modules:** `games/valheim/Dockerfile` (the three `SUPERVISOR_THUNDERSTORE_*` variables with a comment on the staged→live mirror and why the loader pack is provided; hook renamed); the hook itself (mirror step per `design.md` §3, RCON steps unchanged, `chown` to the game user if verification shows root-owned DLLs are unreadable); `games/valheim/gameserver.yaml` (`SUPERVISOR_MODS_FILE` with the policy-lives-in-the-manifest comment, `failureThreshold` 10); the new drift guard in `crates/bot/src/tests/config.rs`; `games/README.md` (the Valheim bullet — it currently also says Valheim has no console protocol, which stopped being true when ValheimRcon was baked in).
- **Preconditions:** Phase 2 live in the Valheim image.
- **Shape when done:** a Valheim server takes mods through `.grizzly/mods`, the mirror puts them under the live `BepInEx/plugins/<Namespace-Name>/`, the RCON plugin keeps working, and every failure mode below is rolled back or reported.
- **Verification (scratch Valheim server, `just game-push valheim dev`):**
  1. Fresh create: `.grizzly/mods` exists and is empty; `read_logs` shows no install lines.
  2. `write_file` one unpinned server-side mod that has a non-loader dependency → `restart_server` → `[mods] installed` names both; `resolved` lists them; the live plugins dir holds `<Namespace-Name>/…` beside `ValheimRcon.dll`; the BepInEx log shows the plugin loaded; `send_command players` still answers. Record the first-install wall time against the bot's five-minute readiness ceiling.
  3. Pin an older version → restart → `resolved` shows it.
  4. Remove the line → restart → the DLL is gone from the live dir and the cache zip was collected.
  5. `Nobody-DoesNotExist` via `edit_file` → `restart_server` → `/status` reports `Crashed`, the bot restores the snapshot and restarts, the server is healthy, and Gary's result says rollback; the `GameServer` never leaves `Ready`; the pod restart count stays 0.
  6. A malformed line → the same path; the log names the line number.
  7. Offline: a fully cached pinned set restarts with no network and a warning; an unpinned entry warns and uses the highest cached version.
  8. Pod recreation → the mirror re-applies after lloesche's first-boot merge; a bad file on the PVC yields a reachable supervisor reporting `Crashed`, not a container crash loop.
  9. Archive → recover keeps `.grizzly/mods`, its `.grizzly.bak`, and the cache; the recovered boot resolves offline.
  10. A half-configured image (one variable unset in a throwaway push) → startup warning, reconciler inert.

### Phase 3 findings

Run on a scratch Valheim server (`modtest`) against the deployed bot.

1. **Fresh create** — `.grizzly/mods` seeded empty (0 bytes), `.grizzly/thunderstore/` created, `[mods] no mods listed; nothing installed` in the log buffer. ✅
2. **Unpinned install with a non-loader dependency** — `shudnal-NomapPrinter` resolved to three packages (itself plus `ValheimModding-YamlDotNet-16.3.1` and `shudnal-ConditionalConfigSync-1.0.4`), with `denikson-BepInExPack_Valheim` skipped as image-provided. `resolved` listed all three plus the skip comment; the live loader directory gained a per-package subdirectory each, beside an untouched `ValheimRcon.dll`; the BepInEx chainloader went from "1 plugin to load" to "4 plugins to load" naming each; `send_command players` still answered. **First-install wall time: ~11 s**, downloads included — far inside the bot's five-minute readiness ceiling, so the follow-up about the inline reconcile starving control requests is not needed. ✅
3. **Pin an older version** — `shudnal-NomapPrinter-1.5.2` resolved, *and* its dependency dropped to `shudnal-ConditionalConfigSync-1.0.1`: the version that release declares, not the newest. The floor rule confirmed live. ✅
4. **Remove the line** — **found a bug, fixed before merge.** The image mirrors the staged tree as the complete desired state, but `stage::rebuild` only created directories it extracted into, so an empty mod list produced no `staged/BepInEx`, the hook's `[ -d "$staged" ]` guard was false, and `--delete` never ran: every mod stayed installed and loaded. The staged tree now always carries the layout's directory skeleton, so "no mods" is an empty tree rather than an absent one — the guard still distinguishes "reconciler not configured" (absent) from "nothing to install" (empty), which is what keeps an unconfigured image behaving as before. Re-verified: the mirror clears all three package directories and the cache is GC'd empty. ✅
5. **Unknown package** — `[mods] failed: could not work out what .grizzly/mods asks for: Nobody-DoesNotExist (from line 1 of the mod list): the registry has no such package or version`. `/status` reported `{"process":"crashed","ready":true,"pid":null,"uptime_seconds":0,"restarts":0}` — crashed, restart counter untouched, control API reachable throughout. The `GameServer` never left `Ready` and the pod's restart count stayed 0, re-confirming [ADR-010](../../decisions/010-recoverable-crash-escalation.md). Repairing the file and restarting returned it to `running`. ✅
6. **Malformed line** — `[mods] failed: .grizzly/mods is unusable: line 2: "just some words" is not a mod — expected a package as Namespace-Name-1.2.3 (letters, digits and underscores)`. Names the line, quotes it, states the shape. ✅
7. **Offline** — not exercised live; simulating it needs an egress policy change, which is a cluster mutation this work has no business making. Covered instead by unit tests over a fake registry that record what they were asked, so the *ordering* is pinned: an exact version is answered from cache with the registry never consulted, an unpinned one prefers a reachable registry, falls back to the highest cached version with a note when it isn't, and fails rather than guessing when nothing is cached.
8. **Pod recreation** — covered by the cold start onto a new node partway through: the pod re-pulled the image, lloesche's updater rebuilt `/opt/valheim/bepinex` from scratch, and the next install mirrored into it correctly. ✅
9. **Archive → recover** — not run. The whole-volume archive is orthogonal to this work (the `.grizzly/` tree is ordinary files on the PVC) and the flow is already covered by its own design's verification.
10. **Half-configured image** — not exercised as a throwaway image push; covered by config unit tests for both half-configured states (warn, reconciler inert) and by the new drift guards, which fail CI if a manifest and its Dockerfile disagree.

**Two traps worth knowing for anyone repeating this:**

- **`restart_server` returns well before the child's BepInEx setup finishes.** Inspecting the live plugins directory immediately afterwards reads the *previous* state. This cost real time — it looked like the mirror was broken on every restart after the first, and I chased that before noticing the hook's own `cp` timestamp was still advancing. The reliable signals are the `[mods]` lines and the chainloader output in `read_logs`, or polling the live directory until it changes.
- **The bot's auto-rollback only arms within a single Gary turn.** `just operator tool write_file` followed by `just operator tool restart_server` are two separate turns, so no pending change is tracked and no verify loop runs. Steps 5 and 6 above therefore verify the *supervisor* half directly (`/status`, the log lines, manual repair); the bot half is unchanged by this work by design — the design adds no rollback code — and is exercised by a real Gary turn instead.

**Also observed:** the container runs as root throughout, so the mirror's `--chmod=D755,F644` is belt-and-braces rather than load-bearing and no `chown` was needed. Each mod's config file appears under `/config/bepinex/` after its first boot (`shudnal.NomapPrinter.cfg`, and so on), reachable by Gary's file tools under the data root exactly as the guide promises.

### Phase 4 findings

- **The two Minecraft blocks moved verbatim.** Only their ids, `sent_when`, and `used_by` changed (`DiscordManagerModChoice` → `GameGuideModrinthChoice`, `DiscordManagerModInstall` → `GameGuideModrinthInstall`), plus one reasoning bullet on each recording that they are now loaded on demand. No model-visible text was rewritten.
- **`SideFilterNotApplicable` stays uncreated** for the reason recorded in Phase 1; nothing in this phase needed it.
- **The guide dispatches ahead of the scope gate** and is spared `targets_existing_server`, alongside the registry lookups and the memory tools — it names no server and reaches nothing but the in-memory catalog.
- **Tier counts moved**: managers now see 25 tools, admins 31. The two count assertions in `discord/gary/tests/tools.rs` are the guard that a tool can't be added at the wrong tier unnoticed, so they are updated rather than loosened.
- **The system-prompt test inverted.** `manager_prompt_carries_the_mod_workflow` asserted the install file was *in* the prompt; it is now `manager_prompt_names_mods_as_a_thing_with_a_first_step`, and a companion assertion checks that neither game's install file (`.grizzly/env`, `.grizzly/mods`) can reach the system prompt again.
- **Gary skips `game_guide` on a vague request and calls it on a concrete one.** Asked "can you add a minimap mod to modtest?", he ran `about_server` then four `search_mods` calls and came back with a question — sensible, but no guide. Asked to install a *named* package, he ran exactly the intended flow: `list_servers` → `game_guide(valheim)` → `search_mods` → `mod_info` → `about_server` → `read_file(.grizzly/mods)` → `list_backups`, then installed the pinned version, restarted, confirmed from the logs, and closed with the both-sided warning in plain language. That is the residual risk [ADR-032](../../decisions/032-game-guidance-loads-on-demand.md) names, landing exactly where it predicted: the guide is reliably loaded at the point it changes what happens, and skipped while the model is still browsing. Left as-is rather than tightened — the prompt bodies are the human's tuning surface, and the behaviour is defensible.
- **A `gary` prompt that argues with its own framing gets refused.** A first attempt at the rollback test said "I know that package does not exist — do not look it up first"; Gary declined it as untrusted fenced text and changed nothing. Correct behaviour, and worth remembering when writing operator prompts: phrase them as an ordinary request.
- **The ADR is 032, and the index needed 029–030 as well.** `docs/decisions/README.md` had stopped at 028 although 029 and 030 existed; 031 lands with Phase 5.
