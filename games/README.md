# games — per-game catalog

The per-*game* config tier (distinct from per-*instance* config, which lives on the PVC and is mutated live by the ops agent — never here). See `docs/design/00-overview.md` → "Config: two tiers".

Each `games/<game>/` directory declares the base template for one game: container image, default env, port shape, resource sizing, persistence needs — expressed as an Agones `GameServer` template plus a NodePort `Service` and a `PersistentVolumeClaim`. These are version-controlled, gated, and change rarely; they can be authored by an AI coding agent at dev time via PR.

**Everything is provisioned on demand.** The bot bakes this whole directory into its image and reads every `games/<id>/` at runtime as its catalog. When a friend issues a Discord command, the bot renders that game's three templates into a uniquely-named instance on a leased NodePort (`7000–7099`), then tears it down when they're done — the template's literal name and nodePort are placeholders the renderer overrides per instance. So a game is provisionable as soon as its directory exists (and its image is pushed); it does **not** need to be listed anywhere else.

`games/kustomization.yaml` is a separate, deliberately-empty concern: it's the *always-on* set that the `grizzly-gameservers-games` Flux Kustomization stands up 24/7. Nothing lives there — the model is all-dynamic. It once held a standalone `minecraft` server used to prove bring-up; that was decommissioned once dynamic provisioning worked. Add an entry there only to resurrect a genuinely always-on server.

Catalog entries:

- `minecraft/` — the reference entry (composite image: grizzly-supervisor as PID 1 wrapping itzg/minecraft-server, driving the Agones SDK `/ready` + `/health`), with native RCON wired for Gary's `send_command` and the in-game `@Gary` chat loop. On the per-instance env overlay (`SUPERVISOR_CHILD_ENV_FILE` / `SUPERVISOR_CHILD_ENV_ALLOWLIST` in its `gameserver.yaml`), which exposes itzg's mod/datapack vars — `TYPE`, `VERSION`, `MODRINTH_PROJECTS`, `MODRINTH_DOWNLOAD_DEPENDENCIES`, `MODRINTH_PROJECTS_DEFAULT_VERSION_TYPE` — for Gary to set per server via `/data/.grizzly/env`.
- `factorio/`, `palworld/` — native Source RCON, so Gary can issue live console commands. Palworld caps its admin/RCON password at 30 chars, handled by the supervisor's `SUPERVISOR_RCON_PASSWORD_MAX_LEN`; Factorio takes its password from a file, seeded by a small wrapper.
- `valheim/` — no native RCON, so the image bakes in BepInEx plus the ValheimRcon plugin to give Gary live console commands and the supervisor a player count. UDP-only, so readiness comes off a log marker (`SUPERVISOR_READY_LOG_PATTERN`) rather than a TCP probe. The first game on the Thunderstore mod reconciler: its manifest declares the per-instance mod list (`SUPERVISOR_MODS_FILE`) and its Dockerfile declares the community, the layout, and the loader pack the image already supplies (`SUPERVISOR_THUNDERSTORE_*`). The supervisor stages the resolved packages under `/config/.grizzly/thunderstore/staged/`; `valheim-pre-server.sh` mirrors that tree into BepInEx's live directories before each start, and `SUPERVISOR_THUNDERSTORE_CONFIG_DIR`/`_CONFIG_KEEP` let the supervisor sweep the settings of mods that are no longer installed out of `/config/bepinex` once a launch has proven good. Also the one game whose join password, display name and browser visibility are env-only — lloesche reads `SERVER_PASS` at launch and no file on the PVC holds it — so its manifest puts `SERVER_PASS`, `SERVER_NAME`, `SERVER_PUBLIC` and `CROSSPLAY` on the per-instance env overlay; `WORLD_NAME`, `SERVER_ARGS` and `VALHEIM_PLUS` are held off it deliberately, pinned by a drift guard.
- `terraria/`, `satisfactory/` — no console protocol the supervisor speaks, so they run **without** live commands (Gary still reads/writes config and restarts). Terraria has no RCON but runs the TShock flavor, whose REST API reports a live player count (ADR-018); Satisfactory comes up and is manageable but full internet multiplayer needs the two-port provisioner follow-up (issue #29).

Mods: a game declares where its mods come from on its `GameServer` `metadata.annotations` — `mod-registry: modrinth | thunderstore`, plus `thunderstore-community` for the latter. The bot reads it at catalog load and points `search_mods`/`mod_info` at that registry; a game without it takes no mods through Gary at all. The install path differs per registry: Minecraft's goes through the per-instance env overlay (itzg re-resolves `MODRINTH_PROJECTS` at every start), while a Thunderstore game's goes through the supervisor's mod reconciler, which resolves `.grizzly/mods` into a staged tree before every launch. Both halves of a Thunderstore game's wiring are cross-checked against the annotations by drift guards in `crates/bot/src/tests/config.rs`.

Settings: most games keep theirs in the game's own config files on the PVC, which Gary finds by browsing. A game whose settings are read from the environment instead declares the per-instance env overlay, and the bot reads that allowlist at catalog load so `game_guide` can name the exact keys rather than restating them in prompt text. Both halves are required together and are cross-checked by a drift guard in `crates/bot/src/tests/config.rs`.

Readiness: the supervisor calls Agones `/ready` only once the game is actually up. Most games prove that with a TCP connect to a port that opens on boot (the game's own TCP port, or its RCON/API port); a UDP-only game with no TCP port at all (Valheim) uses a log-line marker instead. Games with a long first-boot SteamCMD download raise the probe's give-up via `SUPERVISOR_READINESS_TIMEOUT_SECS`.

`_template/` is the skeleton a new game copies.
