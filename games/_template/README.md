# games/_template

Skeleton for onboarding a new game. The `gameserver.yaml` here ships hardened except for the two *rootless* controls — `runAsNonRoot` and `readOnlyRootFilesystem` — because that's what **all 6 current games** do, not a minecraft-only exception. Most upstream game bases bootstrap as root (they chown a data dir to a configurable PUID/PGID, then drop privileges via gosu/su-exec before launching), and a forced non-root user or read-only root filesystem breaks that bootstrap. A documented `nosemgrep` block covers exactly those two and keeps the manifest gate-clean. Everything else in the baseline — `seccompProfile: RuntimeDefault`, `allowPrivilegeEscalation: false`, and `capabilities: drop [ALL]` with only the root bootstrap's working set added back — **is applied and is not optional**: this is the one pod that executes mods, plugins and datapacks chosen by people the platform doesn't vet, and drift guards in `crates/bot/src/tests/config.rs` fail CI if any game (this template included) omits them. Every game's image bakes in the grizzly supervisor as PID 1 (wrapping the game as its child), which owns the Agones SDK lifecycle and serves the in-pod control API the bot/Gary drive; `minecraft/`/`factorio/` are the worked examples. **If your game's base genuinely runs rootless** (no root chown on startup), it's one of the exceptions: delete the `nosemgrep` block and restore the two remaining controls documented below.

## Onboarding a game

1. Copy this directory: `games/_template/` → `games/<game>/`.
2. Fill in `Dockerfile`: `REPLACE_BASE_IMAGE`/`REPLACE_DIGEST` (the game's own upstream image, pinned), `REPLACE_CHILD_CMD` (the command the supervisor launches), and the optional `SUPERVISOR_DATA_DIR`/`SUPERVISOR_RCON_PORT` env vars if they apply. See `games/minecraft/Dockerfile` for a filled-in example.
3. Replace every `REPLACE_*` placeholder in the manifests: `REPLACE_GAME` (name/selector/labels), `REPLACE_IMAGE` (the image this directory's `Dockerfile` builds — a tag or digest, never floating `:latest`), `REPLACE_PORT` / the `containerPort` / `nodePort` (a free port in **7000–7099**, the edge-forwarded band), the data `mountPath`, env, and resource sizing.
4. If the game takes mods, declare where they come from on `gameserver.yaml`'s `metadata.annotations`: `grizzly-gameservers.grizzly-endeavors.com/mod-registry: modrinth | thunderstore`, plus `grizzly-gameservers.grizzly-endeavors.com/thunderstore-community: <slug>` for the latter. That annotation is what points Gary's `search_mods`/`mod_info`/`game_guide` at the right catalog; a game without it is told plainly that it takes no mods here. Then wire the matching install path — the env overlay or the mod list, both under "Notes" below. Drift guards in `crates/bot/src/tests/config.rs` fail CI if the annotation and the image disagree.
5. That's all the wiring — do **not** add `<game>` to `games/kustomization.yaml`. The catalog is all-dynamic: the bot renders each `games/<id>/` into a uniquely-named instance on demand per `/create`, so a new game is picked up automatically. `games/kustomization.yaml` is the always-on set (deliberately empty); adding a game there would run it 24/7. See `games/README.md`.
6. Validate against the live Agones webhook before pushing: `kubectl apply --dry-run=server -k games/<game>/`. That only checks manifest shape — it doesn't build the image or boot the game.
7. Actually try it: `scripts/push-game-image.sh <game> dev` (or `just game-push <game> dev`) builds and pushes the composite image to the in-cluster registry — the operative dev loop for iterating on a supervisor/game change, since game images aren't gate-signed/auto-deployed by CI yet. To drive a `/create` against the new game before anything goes live, run the bot off-cluster with `scripts/local-bot.sh start` (or `just bot-start`): it points `GAMESERVERS_CATALOG_DIR` at this repo's `games/` automatically (the compiled default is the in-container path), so the new `games/<game>/` is picked up with no extra config. See the root `CLAUDE.md`'s "Running & configuring the bot" section for both.

## The security baseline

**Applied by the template, on every game, enforced by test:**

- **`seccompProfile: RuntimeDefault`** (pod level) — the container runtime's own seccomp filter, the same one these images already run under in plain Docker. Kubernetes applies **no** profile unless one is named, so an absent `securityContext` means seccomp-*unconfined*, not "the Docker default". This is the biggest single barrier between a kernel exploit in mod code and the node.
- **`allowPrivilegeEscalation: false`** — sets `no_new_privs`, which blocks *gaining* privilege. A root bootstrap that sheds privilege via gosu/su-exec is unaffected, so this costs the root-bootstrapping bases nothing.
- **`capabilities: drop [ALL]`, adding back only `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETUID`, `SETGID`, `KILL`** — chown/chmod the mounted data dir, become the game user, and signal that now-unprivileged child as PID 1 (root stripped of `KILL` cannot signal another uid). The rest of Docker's default set is gone, `NET_BIND_SERVICE` included: every game here listens above 1024. A game whose base needs fewer may add back fewer; adding anything *outside* this set fails the drift guard.

**The restore target, unset by default** — the two controls the current games' root-bootstrapping bases can't take. Restore them only if your game's base genuinely runs rootless, and delete the matching `nosemgrep` lines when you do:

- **Pod `runAsNonRoot: true` + `runAsUser`/`runAsGroup` + `fsGroup`** — no root in the pod; `fsGroup` makes the data PVC writable by the runtime user. Set `runAsUser` to the UID the game image actually runs as (itzg/minecraft-server = 1000).
- **`readOnlyRootFilesystem: true`** — the game may only write to mounted volumes. Pair it with a writable `/tmp` (emptyDir) plus the data PVC, and add an emptyDir for any other path the image writes to. Unset by default because root-bootstrapping bases write outside the data volume during their chown step.

**Unrelated to the securityContext but part of the same review:**
- **Whole-CPU limits** — fractional CPU limits throttle and the gate flags them; size the limit to the game or omit it to allow bursting.
- **The supervisor, not a readiness sidecar** — earlier revisions of this template bridged a game to the Agones lifecycle with a separate `agones-ready` busybox sidecar. That's been replaced everywhere: the supervisor is baked into the game image itself (this directory's `Dockerfile`), because a separate sidecar can *signal* the game process but can't *relaunch* it — see `docs/design/01-sidecar-agent-interface.md`.

## Notes

- **Data directory for the ops agent (`SUPERVISOR_DATA_DIR`)**: the supervisor scopes Gary's file tools (`browse_files`/`read_file`/`write_file`/`restore_file`) to this directory, defaulting to `/data`. If your game's data PVC `mountPath` is anything other than `/data`, set `SUPERVISOR_DATA_DIR` to match in the `Dockerfile`'s `ENV` — so the agent can reach the game's config and logs. Paths outside this directory (absolute paths, `..`) are refused.
- **Per-instance env overlay (`SUPERVISOR_CHILD_ENV_FILE` / `SUPERVISOR_CHILD_ENV_ALLOWLIST`)**: the per-instance config tier for *environment variables*, for games whose tuning surface is env-driven and re-read on each start. Set `SUPERVISOR_CHILD_ENV_FILE` to a data-root-relative path (convention: `.grizzly/env`) and `SUPERVISOR_CHILD_ENV_ALLOWLIST` to a comma-separated list of the keys an instance may set; before every launch the supervisor injects those keys from that file into the game's environment, overriding the pod template but never the supervisor's own platform injection. **Put both in `gameserver.yaml`, not the `Dockerfile`'s `ENV`** — unlike the rest of the `SUPERVISOR_*` knobs, the allowlist is per-game *policy*, and keeping it in the manifest means widening or narrowing it is a reviewable catalog edit that lands on the next `/create` instead of an image rebuild. The mechanism is off for games that don't set the file, fails closed when the allowlist is empty, and hard-denies any `SUPERVISOR_`-prefixed key plus the game's own RCON password variable regardless of what the allowlist says. Keys are case-sensitive; a malformed line or rejected key is warned about and skipped, never fatal. The supervisor creates the file empty if absent, so Gary's `write_file` always has a prior version to snapshot and the auto-rollback loop covers the very first edit. `games/minecraft/gameserver.yaml` is the worked example (itzg's mod/datapack vars).
- **The reserved `.grizzly/` directory**: the supervisor owns `.grizzly/` under the data root as the home for platform-owned per-instance state. It isn't hidden from Gary's file tools — Gary is its editor.
- **RCON / console access**: only wire `SUPERVISOR_RCON_PORT` (and the matching supervisor dialect flag) if the game speaks it and you want Gary's `send_command` tool to issue console commands. See `games/minecraft/Dockerfile` for the worked example, including ephemeral password minting so no secret is baked into the image or any Kubernetes object.
- **Game port (`SUPERVISOR_GAME_PORT`)**: set this to the TCP port the readiness probe below should connect to. It defaults to `25565` (Minecraft's port) if left unset — every game other than Minecraft (whose port happens to be 25565) must set it explicitly, or the probe silently watches the wrong port. `crates/bot/src/agones/tests/ports.rs`'s `real_game_ports_agree_with_their_readiness_probe` test catches a mismatch between this and the manifest for every real game, so a new game should keep that test green too.
- **Readiness (`SUPERVISOR_READY_LOG_PATTERN`)**: the supervisor only calls Agones `/ready` once the game is actually up, and by default proves that with a TCP connect to `SUPERVISOR_GAME_PORT`. That works for TCP games (Terraria) and for UDP games whose RCON/query port opens on boot (point `SUPERVISOR_GAME_PORT` at that TCP port). A UDP-only game that opens **no** TCP port (Valheim) would never satisfy the connect probe, so set `SUPERVISOR_READY_LOG_PATTERN` to a substring of the game's "server started" log line instead — readiness then fires on the first captured line containing it. Leave it unset to keep the TCP probe.
- **UDP games** (Valheim, etc.): set `protocol: UDP` on the port and Service. The edge forwards UDP+TCP, but TCP MSS clamping doesn't help UDP — a game sending >~1380-byte datagrams needs its own MTU/payload setting (the `wg0` tunnel is 1420). See `docs/activation-status.md`.
- **Thunderstore mods (`SUPERVISOR_MODS_FILE` + the `SUPERVISOR_THUNDERSTORE_*` group)**: the per-instance config tier for *mods*, for the r2modman-shaped games (Valheim, and the rest of the Thunderstore family). The split mirrors the env overlay's and for the same reason: **`SUPERVISOR_MODS_FILE` goes in `gameserver.yaml`** (convention: `.grizzly/mods`) because which file an instance may list mods in is per-game policy, while `SUPERVISOR_THUNDERSTORE_COMMUNITY` (the community slug), `SUPERVISOR_THUNDERSTORE_LAYOUT` (`bepinex`), and `SUPERVISOR_THUNDERSTORE_PROVIDED` (comma-separated `Namespace-Name` packages the image already supplies, i.e. the loader pack) go in the `Dockerfile` because they are facts about the image. The reconciler assembles only when the file *and* the community are both set; either alone warns and stays off. Before every launch the supervisor resolves that list transitively, downloads and validates the zips, and rebuilds a staged tree at `.grizzly/thunderstore/staged/` — it never writes into the game's live loader directory, so **your image needs a pre-launch hook that mirrors the staged tree across**; `games/valheim/valheim-pre-server.sh` is the worked example. A bad mod list fails the launch and reports as `Crashed`, which is what makes the bot restore the file and restart. Two more image facts are optional but wanted wherever the loader writes per-mod settings: `SUPERVISOR_THUNDERSTORE_CONFIG_DIR` (the live settings directory, **data-root-relative** — it has to be on the PVC for the supervisor to reach it) turns on the sweep that removes the settings of a mod that is no longer installed, and `SUPERVISOR_THUNDERSTORE_CONFIG_KEEP` (comma-separated entry names) protects the settings of any plugin the *image* bakes in, whose assembly is not in the staged tree and would otherwise look uninstalled. Leave the directory unset and nothing is swept. Also raise the health `failureThreshold` (Valheim uses 10): that repair re-resolves and may re-download, and it has to land inside the Agones health window. See [ADR-031](../../docs/decisions/031-supervisor-reconciles-thunderstore-mods.md).
- **Multiple advertised ports**: most games need only one leased `NodePort` (the default "remap" path — nothing to configure). If your game's client dials more than one server-advertised port (like Satisfactory's game + Reliable Messaging ports), see `games/satisfactory/service.yaml` for the worked example of the `advertised-ports`/`friend-facing-port`/`port-env.*` annotations that put a game on that path.
- Promote a single `GameServer` to a `Fleet` + shim-managed per-instance NodePort Services once the ops agent/shim owns allocation.
